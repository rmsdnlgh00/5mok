# 재료맨틀 (food-mantle)

꼬맨틀/세만틀 스타일의 "재료로 음식 맞추기" 게임. 재료를 입력하면 오늘의 정답 음식과의
의미적 유사도를 0~100 점수로 알려주고, 음식 이름을 직접 맞히면 승리합니다.

**API 키가 필요 없습니다.** 임베딩은 로컬 모델(Transformers.js)로 계산하며, 배포된 서버는
미리 계산해둔 값만 읽습니다.

## 동작 원리

1. `data/dishes.json` 에 음식별 실제 재료 목록을, `data/extra-ingredients.json` 에 정답과
   무관한 일반 재료들을 정의해둡니다. 둘을 합친 것이 "사전(vocabulary)"입니다.
2. `npm run precompute` 를 실행하면:
   - 사전 전체를 로컬 임베딩 모델로 벡터화해 `data/vocab-embeddings.json` 에 저장합니다.
   - 음식마다 자기 재료 임베딩의 평균("프로필 벡터")을 구합니다.
   - 사전 전체 단어를 각 음식 프로필과의 코사인 유사도 순으로 정렬해
     `data/rankings/<dishId>.json` 에 저장합니다.
3. 서비스가 실행되는 동안에는 **미리 계산된 값만 읽습니다.** 임베딩 모델은 서버에 올리지
   않기 때문에(용량 250MB 제한, 콜드스타트) 런타임 연산이 사실상 0입니다.
4. 오늘의 정답 음식은 **KST 날짜 문자열을 해시**해서 결정하기 때문에, 별도 DB 없이도
   모든 사용자가 하루 동안 같은 문제를 풉니다(자정에 자동으로 바뀜).

### 입력에 대한 4가지 응답

| 입력 | 응답 |
| --- | --- |
| 정답 음식 이름/별칭 | 승리 |
| 사전에 있는 재료 | 0~100 점수 + 사전 내 순위 (정답의 실제 재료면 "재료 일치" 표시) |
| 다른 음식 이름 | 0~100 점수 + 음식 중 순위 (이름·재료 세부 점수 함께 표시) |
| 사전에 없는 단어 | "아직 사전에 없는 재료예요" |

마지막 경우를 줄이려면 `data/extra-ingredients.json` 에 재료를 추가하고 precompute를
다시 돌리면 됩니다.

### 음식 이름을 입력했을 때

"김치찌개"는 정답(된장찌개)이 아니지만 **같은 찌개이고 재료도 많이 겹칩니다.** 그래서
오답으로 끊지 않고 얼마나 가까운 음식인지 점수를 냅니다. 세 가지 신호를 섞습니다
(`scripts/precompute.ts` 의 `WEIGHTS`):

| 신호 | 비중 | 무엇을 잡는가 |
| --- | --- | --- |
| 이름 유사도 | 0.5 | 음식 이름끼리의 임베딩 유사도. "찌개 ↔ 찌개", "탕 ↔ 탕" |
| 재료 겹침 | 0.4 | 두 음식의 재료 목록이 실제로 겹치는 비율(자카드) |
| 재료 프로필 | 0.1 | 재료 평균 벡터끼리의 유사도. 겹치는 재료가 없어도 결이 비슷하면 반응 |

세 신호는 값의 폭이 크게 다르므로(코사인 0.85~0.99 vs 자카드 0~0.5) 후보군 안에서
각각 0~1로 정규화한 뒤 섞습니다. 이때 **정답 자신의 값 1.0을 최대값으로 포함**시킵니다.
그러지 않으면 가장 가까운 음식이 늘 만점을 받아 정답으로 착각하게 됩니다.

정답이 꽃게탕일 때 실제 출력:

```
갈비탕      45.2점   1/62위   (이름 54.9 · 재료 30.0 · 공통 3개)
동태찌개    41.2점   2/62위   (이름 21.9 · 재료 55.6 · 공통 5개)  ← 이름은 멀어도 재료가 겹침
감자탕      38.4점   3/62위   (이름 52.1 · 재료 16.7 · 공통 2개)
김밥        13.8점  52/62위   (이름 19.8 · 재료  0.0 · 공통 0개)
```

공통 재료는 **개수만** 보여줍니다. 어떤 재료인지 알려주면 정답의 재료가 그대로
노출되어 게임이 끝나버리기 때문입니다.

**가중치를 고른 근거** — 음식 63개로 두 지표를 함께 봤습니다(둘 다 낮을수록 좋음).

| 조합 | 같은 조리법 평균순위 | 재료 2개 이상 공유 평균순위 |
| --- | --- | --- |
| **이름 .5 / 프로필 .1 / 겹침 .4** | **5.76** | **9.26** |
| 이름 .5 / 프로필 .5 / 겹침 0 | 6.32 | 12.63 |
| 이름 .35 / 프로필 .15 / 겹침 .5 | 9.05 | 7.74 |

재료 평균 벡터(프로필)만으로는 "실제로 같은 재료를 쓰는가"를 잡지 못합니다. 꽃게탕과
재료 5개를 공유하는 동태찌개가 24위에 머물렀습니다. 두 음식의 재료 목록을 이미 알고
있으므로 겹치는 개수를 직접 세는 편이 정확합니다.

> 음식 점수와 재료 점수는 **서로 다른 분포를 기준으로 환산**한 값이라 같은 축에서 비교할
> 수 없습니다. 그래서 화면에서도 표를 분리해 두었습니다.

## 임베딩 모델

기본값은 `Xenova/multilingual-e5-base` (q8, 768차원)입니다. `data/dishes.json` 의 재료로
"각 음식의 자기 재료가 사전 전체에서 몇 위에 오는가"를 측정해 고른 값입니다(낮을수록 좋음):

| 모델 | 자기 재료 평균순위 (/44) |
| --- | --- |
| **multilingual-e5-base (q8)** | **4.68** |
| multilingual-e5-small (fp32) | 5.20 |
| LaBSE (q8) | 10.72 |
| paraphrase-multilingual-MiniLM-L12-v2 | 20.56 (사실상 무작위) |

e5 계열은 학습 때 쓰인 `query: ` 프리픽스를 붙여야 품질이 나오므로 `lib/embed.ts` 에서
모든 입력에 동일하게 적용합니다.

> ⚠️ 모델을 바꾸면 벡터 공간이 완전히 달라집니다. `EMBEDDING_MODEL` 을 변경했다면 반드시
> `npm run precompute` 를 다시 실행하세요. 섞어 쓰면 유사도가 무의미한 값이 됩니다.

## 로컬 실행

```bash
npm install
npm run precompute   # 최초 1회는 모델 다운로드(수백 MB)로 수 분 소요, 이후 캐시됨
npm run dev
```

`.env.local` 은 없어도 동작합니다. 모델을 바꾸고 싶을 때만 `.env.example` 을 참고하세요.

`npm run precompute` 는 **`data/dishes.json` 이나 `data/extra-ingredients.json` 을 바꿀
때마다** 다시 실행해야 합니다.

`precompute` 앞에는 `npm run validate` 가 자동으로 붙습니다. 재료 이름은 문자열로 정확히
매칭되기 때문에 표기가 조금만 어긋나도 사전이 쪼개지면서 점수가 조용히 나빠집니다.
검증기는 id 중복·이름 충돌·정규화 충돌·고아 랭킹 파일을 잡고, 새로 등장한 재료가 기존
표기와 겹치면(`깨` vs `통깨`) 경고합니다.

## Vercel 배포

1. GitHub에 푸시 후 Vercel에서 저장소 import
2. **환경변수 설정 불필요** (API 키를 쓰지 않음)
3. `data/rankings/*.json` 과 `data/vocab-embeddings.json` 은 **로컬에서 미리 생성해서
   같이 커밋**하세요. Vercel 빌드 중에는 precompute를 실행하지 않습니다 — 임베딩 모델을
   빌드 환경에 내려받으면 느리고, 서버리스 번들 용량 제한에도 걸립니다.
4. 배포 후 재료 데이터를 바꾸면: 로컬에서 `npm run precompute` → 커밋 → 다시 배포.

## 음식 추가/수정하기

`data/dishes.json` 에 아래 형식으로 항목을 추가하고 `npm run precompute` 를 다시
실행하면 됩니다.

```json
{
  "id": "unique-id",
  "name": "음식 이름",
  "aliases": ["다른 이름(선택)"],
  "ingredients": ["재료1", "재료2", "재료3"]
}
```

`data/extra-ingredients.json` 은 **어느 음식의 정답 재료도 아니지만 사용자가 입력할 법한
재료**를 모아둔 곳입니다. 음식의 `ingredients` 에 쓴 재료는 자동으로 사전에 들어가므로
여기에 또 넣을 필요는 없습니다.

### 조심할 것

**① 음식을 추가하면 모든 날짜의 정답이 바뀝니다.**

```ts
const idx = hashString(dateStr) % list.length;   // ← 음식 개수로 나눈다
```

개수가 바뀌는 순간 나머지가 전부 달라져서 오늘의 정답도 바뀝니다. 개발 중에는 상관없지만
**사람들이 실제로 플레이하기 시작한 뒤에 음식을 추가하면 풀던 문제가 중간에 바뀝니다.**
배포 후에는 자정 직후에 추가하거나, 정답을 날짜에 고정하는 방식으로 바꿔야 합니다.

**② 음식을 지우거나 `id` 를 바꾸면 옛 랭킹 파일이 남습니다.** precompute는 새로 쓰기만 하고
지우지 않습니다. `npm run validate` 가 고아 파일을 찾아주니 안내대로 지우면 됩니다.

**③ 재료 표기는 기존 사전과 정확히 맞춰야 합니다.** 입력 정규화는 공백 제거와 소문자화만
합니다. `돼지 고기` → `돼지고기` 는 매칭되지만 `대파` 와 `파`, `다진마늘` 과 `마늘` 은
서로 다른 단어입니다. 기존 표기는 이렇게 확인합니다:

```bash
node -e "console.log(Object.keys(require('./data/vocab-embeddings.json')).join(' '))"
```

## 지금 버전에서 단순화한 부분 (다음에 개선하면 좋은 것들)

- **음식 63개 + 재료 사전 305단어**입니다. 음식을 늘릴수록 게임이
  풍부해지고, 재료별 "핵심 재료 vs 부재료" 가중치를 주는 것도 고려해볼 만합니다.
- 소형 다국어 모델이라 한국어 단어 유사도에 가끔 엉뚱한 결과가 섞입니다(예: 한자어 음절을
  공유하는 "대추"와 "고추"를 가깝게 봄). 음식/재료 수를 늘리거나 더 큰 모델을 쓰면 완화됩니다.
- 오탈자/유사어 처리(예: "고추장" vs "고추장양념")가 없습니다. 필요하면 사전에
  동의어 매핑 테이블을 추가하는 게 좋습니다.
- 하루 지난 정답을 보여주는 "어제의 정답" 기능, 공유하기(결과 이미지) 같은 건
  포함하지 않았습니다.
- 현재는 세션 저장이 없어서 새로고침하면 시도 기록이 날아갑니다. 필요하면
  localStorage에 오늘 날짜 기준으로 저장하면 됩니다.
